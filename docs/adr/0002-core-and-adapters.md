# 0002. A portable core and one adapter per platform

Status: accepted (2026-11-20)

## Context

Domain aliases were tied to Netlify: the sync script called the Netlify API and wrote `_redirects`, and the redirects page was generated by parsing that file. The path parameters in `from` (`/:url/:device`) were Netlify behavior, never defined here. The same aliases now have to be served by a Docker image on CapRover (with proxying as well as redirects), and perhaps by Cloudflare Workers later.

## Decision

`domainAliases.json` stays the single source of truth. A core (`Errors`, `Protocols`, `Schemas`, `Utils`, `Generators`) validates it and defines the matcher once: how a host and path pattern match and how `:param` values go into `to`. An adapter per platform implements one port. Config-generating adapters (Netlify, CapRover domains) write configuration or call an API; runtime adapters (Docker server, Cloudflare Worker) answer requests with the matcher. Each adapter declares its capabilities and `sync` fails when an alias needs one it lacks. The alias gets an optional `mode` (`redirect` by default, `proxy`), so the current file stays valid.

## Consequences

- The core imports no Node built-in, enforced by lint and a test, so the matcher runs unchanged in a Worker.
- Adding a platform is one adapter plus one setup, with no change to the others.
- A semantic difference between platforms is a declared capability, not a production surprise.
- Netlify keeps redirecting by its own engine, so its behavior is matched by tests of the generated file, not by the matcher.
